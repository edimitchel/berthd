berth works with the tools around it in both directions: tools drive
berth through its CLI, and berth drives tools through hooks. Every event
records the tool it came from, so a change never bounces back and forth
between two tools.

## Agent tools → berth

### Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Grok CLI

```sh
berth integrations install claude     # on a laptop
berthd integrations install claude    # on a box, where agents usually run
berth integrations install all
```

`berthd install` (which `berth add ssh` and the install script run) already
does this on a box for every agent CLI it finds there, unless given
`--no-integrations`; for one installed later, the app offers to when it
first starts that agent on the box, and `berth doctor BOX` (or
`berthd doctor` on the box) warns about each agent CLI without its hooks,
with the command that installs them.

- **Claude Code**: installs berth's skills in `~/.claude/skills/` and
  `SessionStart` / `UserPromptSubmit` / `PostToolUse` / `PermissionRequest` /
  `Notification` / `Stop` / `StopFailure` / `SessionEnd` hooks in
  `~/.claude/settings.json`. Only permission and question notifications mean
  "needs you"; the idle reminder and login notices are ignored.
- **Cursor**: appends `sessionStart`, `beforeSubmitPrompt` and `stop` hooks to
  `~/.cursor/hooks.json`, after any hooks already there (Orca's are kept).
- **Codex**: installs berth's skills in `~/.agents/skills/`, where Codex
  reads user skills (a copy an older berth left in `~/.codex/skills/` is
  removed), adds `SessionStart` / `UserPromptSubmit` / `PermissionRequest` /
  `Stop` hooks to `~/.codex/hooks.json` (trust them once in Codex with
  `/hooks`), and a `notify` line to `~/.codex/config.toml` for versions
  without hooks. Codex runs a single notify program, so when the config
  already sets one to something else, berth leaves it and prints the line to
  change yourself.
- **Gemini CLI**: `SessionStart` / `BeforeAgent` / `Notification` /
  `AfterAgent` / `SessionEnd` hooks in `~/.gemini/settings.json`.
- **OpenCode**: a small plugin, `~/.config/opencode/plugin/berth.js`, that
  runs the hook when a session gets busy, asks for a permission, or goes idle.
- **Grok CLI**: `SessionStart` / `UserPromptSubmit` / `PostToolUse` /
  `Notification` / `Stop` / `StopFailure` / `StopCancelled` / `SessionEnd`
  hooks in `~/.grok/hooks/berth.json`. Only `permission_prompt` (and
  Claude-compatible question types) mean "needs you"; `idle_prompt` and
  `task_complete` settle a turn that never reported `Stop`, and are not
  questions. Grok Build has no skill or MCP install path in Berth yet.

After an upgrade, berthd brings hooks it installed before up to date when it
starts. Every session berth starts has `BERTH_SESSION` (and, for an agent
preset, `BERTH_AGENT`) in its environment; the hook sends it along, so berth
knows which session a hook came from when agents share a worktree. When
berthd is down, `berthd hook` keeps the event in `~/.berth/box/spool/` and
berthd publishes it, in order, when it starts. What each agent can report,
and how berth fills the gaps, is in
[turns](/concepts/sessions-and-agents#turns).

Installs are idempotent, keep every existing setting, back up the previous
file to `*.berth-backup`, and refuse to touch a file that is not valid JSON.

The hooks run `berth hook TOOL EVENT`, which turns the tool's payload into an
event (`agent.finished`, `agent.waiting`, `agent.started`, `agent.ready`, `agent.exited`). Only identifiers and
the working directory are kept: prompts, messages, and transcripts never
leave the tool. A hook never fails or blocks the tool that called it.

### Skills

berth ships four skills, embedded in the binary:

| Skill | Teaches agents to |
| --- | --- |
| `berth` | find their way around: boxes, repos, worktrees, tasks, sessions, the worktree's `$BERTH_*` variables and ports, `.berth/config.json`, services |
| `berth-orchestrate` | prompt, wait for, check, loop, hand off to and review with other agents, and never answer for the human |
| `berth-preview` | run the dev server on the worktree's port and open it in the user's Berth app (`berthd preview`) |
| `berth-hooks` | write hooks and gates at the right scope, with the event catalog |

Install them for the box's user, or inside one repository for just that
project, for Claude Code, Codex, or both:

```sh
berthd skills                                         # what is installed where
berthd skills install                                 # all, for both agents, for this user
berthd skills install berth-preview --agent claude --target project --location shop
berthd skills install --target project --location shop --commit   # visible to git, to share
berthd skills uninstall berth-hooks
berth skills devl install                             # the same from a laptop
```

| Target | Claude Code | Codex |
| --- | --- | --- |
| user | `~/.claude/skills/<skill>/` | `~/.agents/skills/<skill>/` |
| project | `<repo>/.claude/skills/<skill>/` | `<repo>/.agents/skills/<skill>/` |

Project skills are listed in the repository's `.git/info/exclude` so they are
not committed, unless installed with `--commit`. `berthd skills` reports each
copy as installed, outdated (berth has a newer version: install again) or
missing; the app shows the same in Settings → Agents and in a project's
settings. Removing only deletes a folder whose `SKILL.md` is berth's skill of
that name.

The API is `GET /v1/skills[?location=L]`, and `POST /v1/skills/install` and
`POST /v1/skills/uninstall` with `{skills, agent, target, location, commit}`.
Changes announce `skills.installed` and `skills.removed`, and
`before:skills.install` and `before:skills.uninstall` gates can refuse them.

The skills tell agents never to share a port publicly unless a person asked,
and never to answer an agent's question on the user's behalf.

### Anything else

Any script can announce an event:

```sh
berth emit agent.finished path="$PWD" --origin=mytool     # on a laptop
berthd emit deploy.done url=https://… --origin mytool      # on a box
```

## Worktrees from any tool

berthd watches its locations. A worktree created by another app, an agent,
or plain `git worktree add` shows up in berth and produces a
`worktree.created` event with origin `detected`. Nothing needs configuring in
those tools.

## berth → tools

berth drives other tools through hooks and plugins rather than adapters
built into it: a hook on `worktree.created` can register the worktree with
any tool that has a CLI, and a plugin can ship those hooks along with its UI.
See [hooks](/guides/hooks) and [plugins](/guides/plugins).

`berth events` streams every event from the laptop and all its boxes; the
full list is in [events and gates](/reference/events).
